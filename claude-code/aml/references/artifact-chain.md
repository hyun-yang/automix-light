# 단계별 문서의 역할과 관리 방법

aml이 작성하는 문서는 **다음 단계의 작업 기준**입니다. 개발 목적, 요구사항, 계획, 결과를 파일별로 나누어 기록합니다.

| 파일 | 기록하는 내용 | 활용하는 단계 |
|---|---|---|
| `intent.md` | 앱을 만드는 목적과 해결하려는 문제 | `/aml:new`에서 요구사항을 구체화할 때 참고 |
| `spec.md` | 필요한 기능과 완성 기준 | `/aml:go`의 검증, `/aml:review`의 요구사항 점검 |
| `task.md` | 작업 순서, 예상 위험, 검증 방법 | `/aml:go`의 구현 순서와 계획 변경 확인 |
| `progress.md` | 수행한 작업, 작업 지표, 리뷰 결과 | `/aml:status`의 진행 요약, `/aml:rule`의 반복 실수 확인 |
| `REVIEW.md` | 코드 리뷰 범위와 기준 | `/aml:review`에서 일관된 기준으로 점검 |
| `CLAUDE.md` | 프로젝트 안내, 실행·검증 방법, 개발 규칙 | Claude Code가 매 세션 시작 시 참고 |

같은 내용을 여러 파일에서 관리하면 일부만 수정되어 내용이 달라질 수 있습니다. 확인하려는 내용에 따라 다음 파일을 기준으로 삼습니다.

| 확인할 내용 | 기준 문서 |
|---|---|
| 앱을 만드는 이유 | `intent.md` |
| 구현 완료를 판단하는 기준 | `spec.md`의 완성 기준 |
| 현재 작업과 완료 여부 | `task.md`의 체크박스 |
| 구현 과정에서 내린 결정과 이유 | `progress.md`의 메모 |
| 코드 리뷰에서 확인할 범위 | `REVIEW.md` |
| 앱 실행과 검증 방법 | `CLAUDE.md`의 “확인하는 법” |

## 문서 관리 원칙

1. **단계별 결과를 커밋합니다.** 언제 무엇을 결정하고 변경했는지 `git log`로 확인할 수 있습니다. 필요한 경우 커밋 단위로 변경을 되돌릴 수도 있습니다.
2. **구현 계획이 달라지면 문서도 함께 수정합니다.** 코드만 바뀌고 `task.md`가 그대로이면 이후 작업에서 잘못된 계획을 참고하게 됩니다. 계획 변경은 관련 코드와 같은 커밋에 포함합니다.
3. **이전 기록을 보존합니다.** 이전 기획은 `intent.md` 아래에, 수정한 버그의 검증 기준은 `spec.md`에, 작업 결과는 `progress.md`에 남깁니다. 이후 작업에서 결정 배경을 확인하고 같은 문제의 재발 여부를 점검할 수 있습니다.

## 다른 도구와 함께 사용할 때

노션·지라·트렐로에도 계획을 기록한다면, 내용이 달라졌을 때 **어느 쪽을 기준으로 삼을지** 정해야 합니다.

- **저장소를 기준으로 관리** — 혼자 개발할 때 간단한 방식입니다. 마크다운 파일에서 내용을 관리하고, 노션 등에는 해당 파일의 링크를 남깁니다.
- **외부 도구를 기준으로 관리** — 팀에서 이미 쓰는 도구가 있다면 노션·지라의 내용을 기준으로 삼습니다. 세션 시작 시 필요한 내용을 프로젝트 문서에 반영하고, 작업 후 결과를 외부 도구에도 반영합니다.
- **문서 간 링크 유지** — 양쪽에 관련 문서의 링크와 기준 문서가 무엇인지 표시해, 최신 내용을 찾을 수 있게 합니다.

기준 문서를 정한 뒤에도 변경 사항을 다른 쪽에 반영하는 절차가 필요합니다. 두 곳의 내용이 다르면 기준 문서를 먼저 확인합니다.

## 팀 협업으로 확장할 때

같은 문서 구성을 팀에서도 사용할 수 있습니다. PR 리뷰에서는 `spec.md`, `task.md`, `REVIEW.md`를 함께 참고해 요구사항과 계획을 충족했는지 확인합니다. 자세한 내용은 [프로젝트 확장과 팀 협업](next-steps.md)을 참고하세요.
