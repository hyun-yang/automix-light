# /aml:new — 대화로 지도를 그린다

사용자의 아이디어: $ARGUMENTS

지금 함께 일하는 사람은 초보자다. 코드는 못 읽지만, 질문에는 답할 수 있고 눈으로 본 것에는 반응할 수 있다. 이 명령의 목표는 초보자 머릿속의 그림을 파일 몇 개로 옮기는 것이다 — 구현은 /aml:go 의 몫이다. 대화와 산출물(intent.md·spec.md·task.md·progress.md, 템플릿의 제목까지)은 모두 **한국어**로, 초보자가 알아듣는 쉬운 말로 쓴다. (기계가 붙이는 측정 줄만 observe.py 가 만든 형식 그대로 둔다.)

## 1. 이미 하던 일이 있는지 확인

프로젝트 루트에 spec.md 와 task.md 가 있고 끝나지 않은 할 일이 남아 있으면, 이어서 할지(/aml:go 안내) 새로 시작할지 사용자에게 묻는다. 새로 시작한다면 이전 작업 요약을 progress.md 에 남긴 뒤 spec.md 와 task.md 를 새로 쓴다. 이어서 하기로 했더라도 2단계의 준비물은 확인하고 넘긴다.

## 2. 지형 살피기와 준비물 갖추기

기존 코드가 있으면 훑어보고 언어·프레임워크·구조를 파악한다. 빈 프로젝트면 건너뛴다.

이어서 준비물을 확인한다 — 인터뷰를 하기 전에, 파일을 쓰기 전에.

- **CLAUDE.md** — 프로젝트 루트에 있는지 확인만 하고 기억해 둔다. **있으면 절대 덮어쓰지 않는다.** 없으면 5단계에서 인터뷰 결과로 만든다.
- **REVIEW.md** — 있는지 확인만 한다. **있으면 덮어쓰지 않는다.** 없으면 5단계에서 템플릿 그대로 만든다.
- **규칙 카드** — `.claude/skills/*/SKILL.md` 가 있으면 전부 읽어 둔다. 이 프로젝트에서 이미 정해 둔 규칙이니, 3~5단계 내내 지켜야 할 제약으로 삼는다.
- **git** — 저장소가 아니면 알리고 바로 초기화한다. 이미 저장소면 아무것도 하지 않는다(남의 브랜치 이름도 바꾸지 않는다).

  ```bash
  git rev-parse --is-inside-work-tree >/dev/null 2>&1 \
    || git init -b main 2>/dev/null \
    || { git init && git symbolic-ref HEAD refs/heads/main; }
  ```

  둘째 갈래는 `-b` 를 모르는 옛 git 대비다 — 첫 커밋 전이라 `master` 대신 `main` 을 가리키게 하면 된다. 사용자에게는 한 줄로 알린다: "되돌리기가 쉽도록 git 을 준비하고 기본 브랜치를 main 으로 맞췄습니다."

## 3. 처음 한 말을 그대로 남긴다 — intent.md

인터뷰로 다듬기 **전에**, 사용자가 왜 이걸 만들고 싶어 했는지를 사용자의 말로 먼저 적는다. 나중에 길을 잃었을 때 돌아올 원본이다.

`${CLAUDE_PLUGIN_ROOT}/templates/intent.template.md` 를 따라 프로젝트 루트에 `intent.md` 를 만든다(이미 있으면 **맨 위에** 오늘 날짜로 새 항목을 추가하고 지난 항목은 그대로 둔다). 채우는 법:

- 사용자의 문장을 고쳐 쓰지 않는다. 전문 용어로 번역하지 않는다.
- 아직 모르는 칸은 비우지 말고 "아직 모름"이라고 적는다 — 그게 바로 다음 단계에서 캐낼 것이다.
- 한두 가지 정도만 짧게 되묻는다(무엇이 불편한지, 잘 되면 어떤 모습인지). 본격적인 질문은 4단계에서 한다.

git 저장소면 여기서 한 번 커밋한다: `intent: <한 줄>`. 왜 만들기로 했는지가 기록으로 남는다.

## 4. 모르는 것 캐내기 — 인터뷰

초보자의 지도에는 네 구역이 있고, 구역마다 끌어내는 방법이 다르다.

- **KK (아는 것을 아는)** — 사용자가 이미 말한 것. 다시 묻지 말고 그대로 적는다.
- **UU (모르는 줄도 모르는)** — 생각조차 해 보지 못한 정할 거리. **사각지대 훑기**: 먼저 "이런 걸 만들 때 보통 이런 걸 정합니다" 목록을 보여 준다. 목록을 보는 것만으로 UU 가 KU 로 바뀐다.
- **KU (모르는 걸 아는)** — 정해야 하는데 아직 안 정한 것. 전문 용어 없이, 선택지와 함께, 한 번에 하나씩 묻는다. 모든 질문에 "잘 모르겠어요 — 추천해 주세요" 선택지를 넣고, 그걸 고르면 선택과 이유를 대신 정해 준다.
- **UK (말로는 못 하지만 아는)** — 설명은 못 해도 보면 안다. 화면이나 디자인이 중요한데 사용자가 취향을 말로 못 하면, 완전히 다른 느낌의 화면 목업 3~4개를 HTML 파일 하나에 만들어 고르게 한다. 고른 목업이 참고 자료(지도의 일부)가 된다.

질문 수는 규모에 맞춘다 — 작은 기능이면 3개쯤, 새 앱이나 프레임워크 선택이 걸리면 7개쯤. 구조가 바뀔 수 있는 질문을 먼저 한다.

2단계에서 읽어 둔 규칙 카드가 있으면 그 규칙에 맞는 선택지를 먼저 제시한다. 규칙과 사용자의 요구가 부딪히면 임의로 정하지 말고, 그 사실을 알리고 어떻게 할지 물어본 뒤 결과를 spec.md 의 "걱정되는 것"에 남긴다.

## 5. 산출물 쓰기

`${CLAUDE_PLUGIN_ROOT}/templates/` 의 템플릿을 따라 프로젝트 루트에 만든다.

- **spec.md** — 인터뷰 결과를 담는다.
  - "완성 기준"은 초보자가 직접 써 보고 확인할 수 있는 문장으로 쓴다 — 이 목록이 /aml:go 의 검증 기준이고, 앞으로 계속 쌓여 가는 확인 목록이 된다.
  - 인터뷰에서 정한 것은 "정한 것들" 표에, 고른 목업·화면 캡처·"○○ 앱처럼"은 "참고 자료 (지도)"에 적는다.
  - **"걱정되는 것"** 에는 만들기 전에 미리 표시해 둘 것을 적는다 — 규칙 카드와 부딪히는 것, 남의 정보·돈·안전이 걸린 것, 둘 다 만족시킬 수 없는 요구. 없으면 "없음". 여기 적은 것은 사용자에게 한 번 더 확인받는다.
- **task.md** — 순서대로 진행할 굵은 할 일. 할 일 하나 = 한 번에 끝내는 한 덩어리. 구간마다 **바뀌는 파일 / 위험 / 증명** 세 줄을 채운다. 아직 모르면 "아직 모름"이라고 적되, 위험과 증명은 되도록 채운다 — /aml:go 가 이 두 줄을 보고 "맡겨도 되는 일인지"와 "무엇으로 다 됐다고 할지"를 판단한다.
- **progress.md** — 없으면 템플릿으로 만들고, 오늘 날짜로 "계획 세움" 기록을 하나 남긴다.
- **CLAUDE.md** — 2단계에서 없다고 확인된 경우에만, claude.template.md 를 따라 인터뷰 답으로 채워 쓴다. Claude Code 가 다음 세션부터 자동으로 읽는 파일이니 **한 페이지를 넘기지 않게** 짧고 정확하게. "확인하는 법"에는 실행·테스트 명령과 함께 **잘 됐을 때 어떻게 보이는지**를 적는다. 인터뷰에서 안 나온 칸은 억지로 되묻지 말고 `<아직 안 정함>` 으로 둔다.
- **REVIEW.md** — 2단계에서 없다고 확인된 경우에만, review.template.md 를 그대로 만든다. 프로젝트에 맞게 고칠 게 보이면 한두 줄만 손본다.

## 6. 확인받기

spec.md 를 쉬운 말로 요약해 보여 주고 검토받는다. "걱정되는 것"이 있으면 그것부터 짚는다. git 저장소면 만든 파일들을 커밋한다(`plan: <한 줄>`). 확인이 끝나면 이렇게 안내한다: "/aml:go 를 실행하면 구현을 시작합니다."
