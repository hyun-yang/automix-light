# 할 일 앱으로 살펴보는 전체 사용 흐름

aml로 간단한 할 일 앱을 기획하고, 구현·검증한 뒤, 사용하면서 발견한 문제를 개선하는 예시입니다. 아래 대화와 작업 지표는 설명을 위한 예시이며 실제 실행 결과는 달라질 수 있습니다.

## 명령어 구성

기존 명령어 4개에 리뷰, 개선 계획, 개발 규칙을 위한 명령어 3개가 추가되어 총 7개를 제공합니다.

| 구분 | 명령어 |
|---|---|
| 기존 명령어 | `/aml:new`, `/aml:go`, `/aml:status`, `/aml:doctor` |
| 추가된 명령어 | `/aml:review`, `/aml:next`, `/aml:rule` |

기본 작업은 `/aml:new`로 계획을 세우고 `/aml:go`로 구현하는 순서입니다. `/aml:go`가 끝날 때 리뷰도 자동으로 진행합니다. 나머지 명령어는 필요할 때 사용합니다.

## 0단계: 시작 전 점검 (선택)

```text
/aml:doctor
```

빈 폴더라면 `spec.md`, `task.md`, `progress.md`가 없다는 안내와 함께 `/aml:new` 실행을 권합니다. 처음 시작할 때는 이 점검을 건너뛰고 바로 `/aml:new`를 실행해도 됩니다.

## 1단계: 아이디어 구체화와 작업 계획

```text
/aml:new "할 일을 적고 체크하는 앱, 브라우저에서 여는 HTML 파일 하나로"
```

Claude는 다음 순서로 진행합니다.

1. **프로젝트 준비** — Git 저장소가 아니면 `main` 브랜치로 초기화합니다. `CLAUDE.md`와 `REVIEW.md`가 없으면 생성하고, 기존 파일은 유지합니다.
2. **개발 목적 기록** — 질문을 시작하기 전에 사용자의 표현을 `intent.md`에 기록하고 `intent: 할 일 앱`으로 커밋합니다.
3. **요구사항 확인** — 완료한 할 일의 처리, 마감일, 순서 변경, 데이터 저장처럼 결정이 필요한 항목을 안내합니다. 그다음 선택지가 있는 질문을 약 5개 하고, 화면은 목업 3~4개 중에서 고르도록 합니다.
4. **계획 문서 작성** — `spec.md`에 완성 기준과 예상되는 문제를, `task.md`에 작업별 변경 파일·위험·검증 방법을 정리합니다. `progress.md`도 생성하고 계획을 검토받은 뒤 `plan: 할 일 앱`으로 커밋합니다.

`intent.md`에는 다음과 같은 내용을 남깁니다.

```text
- 무엇이 불편한가: 포스트잇에 적으니까 자꾸 잃어버려요.
- 원하는 결과: 노트북을 열면 오늘 할 일이 보였으면 좋겠어요.
- 아직 모르는 것: 어떤 기능을 정해야 하는지 잘 모르겠어요.
```

`task.md`의 예시는 다음과 같습니다. “증명” 항목에는 작업이 제대로 완료되었는지 확인할 방법을 적습니다.

```markdown
## 1. 화면과 저장

- 바뀌는 파일: todo.html
- 위험: 낮음
- 증명: 브라우저에서 할 일 3개를 추가한 뒤 새로고침해도 목록이 유지된다.

- [ ] 1.1 목록 화면과 추가 창
- [ ] 1.2 완료 표시와 삭제
- [ ] 1.3 브라우저에 저장 (새로고침해도 유지)
```

## 2단계: 구현과 검증

```text
/aml:go
```

각 작업은 **계획 확인 → 구현 → 검증 → 기록 → 커밋** 순서로 진행합니다.

예를 들어 “1.1 목록 화면과 추가 창”은 다음과 같이 처리합니다.

```text
위험이 낮고 검증 방법이 정해져 있음을 안내
  → 화면 구현 후 브라우저에서 동작 확인
  → progress.md에 결과와 작업 지표 기록
     - 측정: claude-opus-4-8 · 3분 11초 · 토큰 입력 8.2k / 출력 2.4k · 예상 비용 $0.19
  → feat: 1.1 목록 화면과 추가 창 커밋
```

나머지 작업도 같은 순서로 진행합니다. 모든 작업이 끝나면 다음 절차로 마무리합니다.

1. **별도 검증** — `verifier` 에이전트가 직접 실행해 완성 기준 충족 여부를 확인합니다.
2. **완성 기준 표시** — 통과한 기준은 `spec.md`에서 `- [ ]`를 `- [x]`로 변경합니다.
3. **코드 리뷰** — `REVIEW.md`를 기준으로 버그, 보안 문제, 요구사항 충족 여부를 점검하고 “중요 0 · 사소 2”처럼 결과를 보고합니다.
4. **최종 커밋** — 작업을 마무리하고 앱을 직접 사용한 뒤 `/aml:next`를 실행하도록 안내합니다.

## 3단계: 사용 후 개선 사항 정리

```text
/aml:next
```

Claude는 앱이 예상대로 동작했는지, 불편하거나 이상했던 점은 무엇인지, 추가로 필요한 기능이 있는지 질문합니다.

| 사용자의 의견 | 반영 방법 |
|---|---|
| “긴 제목을 넣으면 글자가 잘려요.” | 작은 수정이므로 `task.md`에 작업을 추가합니다. |
| “달력에서도 봤으면 좋겠어요.” | 새 기능이므로 `intent.md` 맨 위에 정리하고 `/aml:new`로 기획합니다. |
| “알림 기능은 나중에 추가할게요.” | 이번에 구현하지 않는 이유를 `intent.md`나 `progress.md`에 기록합니다. |

추가한 수정 작업은 다음 명령으로 진행합니다.

```text
/aml:go
```

버그를 수정할 때는 문제를 재현하는 테스트나 확인 절차를 먼저 준비합니다. 수정 중임을 나타내는 `.aml/FIXING` 파일이 있는 동안에는 작업 차단 훅이 테스트 파일 변경을 막습니다.

수정한 버그는 `spec.md`의 완성 기준에도 남겨 이후 작업에서 다시 확인합니다.

```markdown
- [x] 긴 제목도 잘리지 않는다 (2026-09-06 수정)
```

## 필요할 때 사용하는 명령어

```text
/aml:review          # 커밋 전에 변경 내용을 추가로 점검
/aml:review 전체     # 기존 코드를 포함한 전체 코드 점검
/aml:rule            # 반복된 지적이나 실수를 개발 규칙으로 정리
/aml:status          # 진행 상황과 지표 확인, 원하면 이해도 퀴즈 진행
/aml:doctor          # 작업 준비 상태나 설정 문제 점검
```

예를 들어 `/aml:rule`이 `progress.md`에서 “저장 여부 확인 누락”이 두 번 반복된 것을 발견하면, `CLAUDE.md`의 “Claude가 자꾸 틀리는 것” 항목에 예방 규칙을 추가합니다. 여러 단계로 이루어진 절차라면 `.claude/skills/<이름>/SKILL.md`에 규칙 카드로 작성합니다.

## 전체 흐름 요약

```text
/aml:new → /aml:go → 직접 사용 → /aml:next
  기획     구현·검증               개선 사항 정리
                                  ├ 작은 수정 → /aml:go
                                  └ 새 기능·방향 변경 → /aml:new
```

작업 중 언제든 `/aml:status`로 진행 상황을 확인하고, `/aml:review`나 `/aml:doctor`로 필요한 점검을 할 수 있습니다. 다음 기능을 기획할 때도 기존 문서와 개발 규칙을 참고하며 작업을 이어갑니다.
