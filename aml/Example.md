# Example
1. 명령어 개수

4개 → 7개 입니다.

┌────────────────────────────────────────────────┬─────────────────────────────────────┐
│                    기존 4개                      │           새로 추가된 3개              │
├────────────────────────────────────────────────┼─────────────────────────────────────┤
│ /aml:new · /aml:go · /aml:status · /aml:doctor │ /aml:review · /aml:next · /aml:rule │
└────────────────────────────────────────────────┴─────────────────────────────────────┘

이 중 매번 쓰는 건 실질적으로 2개(/aml:new → /aml:go)입니다. /aml:review 는 /aml:go 가 끝날 때 자동으로 한 번 돌고, 나머지는 필요할 때만 부릅니다.

2. ToDo 앱 한 판 — 전체 흐름

0단계 (선택) — 시작 전 점검

/aml:doctor

▎ 빈 폴더면 "❌ spec.md/task.md/progress.md 가 없습니다 → /aml:new 부터 하세요". 처음이면 건너뛰고 바로 /aml:new 해도 됩니다.

1단계 — 지도 그리기

/aml:new "할 일을 적고 체크하는 앱, 브라우저에서 여는 HTML 파일 하나로"

Claude 가 순서대로 하는 일:

1. 준비물 — git 초기화(main 브랜치) + CLAUDE.md·REVIEW.md 생성 (이미 있으면 손대지 않음)
2. intent.md — 인터뷰 전에 사용자 말 그대로 기록 → 커밋 intent: 할 일 앱
- 무엇이 불편한가: 포스트잇에 적으니까 자꾸 잃어버려요
- 원하는 결과: 노트북 열면 오늘 할 일이 보였으면
- 아직 모르는 것: 아직 모름
3. 인터뷰 — "보통 이런 걸 정합니다: 끝낸 할 일은 지울까 남길까 · 마감일 · 순서 바꾸기 · 컴퓨터 꺼도 남기기…" 를 먼저 보여 준 뒤(UU→KU), 선택지가 있는 질문 5개쯤. 화면 취향은 목업 3~4개 중에서 고름(UK)
4. 산출물 — spec.md(완성 기준 + 걱정되는 것) · task.md(구간별 바뀌는 파일/위험/증명) · progress.md → 커밋 plan: 할 일 앱

만들어지는 task.md 는 이런 모양입니다:

## 1. 화면과 저장
- 바뀌는 파일: todo.html
- 위험: 낮음
- 증명: 브라우저에서 할 일 3개 추가 후 새로고침해도 남아 있음

- [ ] 1.1 목록 화면과 추가 창
- [ ] 1.2 체크 표시와 지우기
- [ ] 1.3 브라우저에 저장(새로고침해도 유지)

2단계 — 만들기

/aml:go

할 일 하나마다: 계획 확인 → 구현 → 검증 → 기록 → 커밋

1.1 목록 화면과 추가 창
  → "위험 낮음 + 확인 방법 있음 → 맡겨 두셔도 됩니다"
  → 만들고 브라우저로 확인
  → progress.md 기록
     - 측정: claude-opus-4-8 · 3분 11초 · 토큰 입력 8.2k / 출력 2.4k · 예상 비용 $0.19
  → 커밋 feat: 1.1 목록 화면과 추가 창
1.2 …  1.3 …

다 끝나면 자동으로:

① verifier 독립 확인 — 새 눈으로 직접 실행 → "완성 기준 6개 중 6개 됨"
② 완성 기준 체크 (spec.md 의 - [ ] → - [x])
③ 리뷰 (REVIEW.md 3패스) → "중요 0 · 사소 2"
④ 마무리 커밋 + "직접 써 보시고 /aml:next 를 실행하세요"

3단계 — 써 보고 한 바퀴 더

/aml:next

▎ "① 잘 되던가요? ② 안 되거나 이상했던 것은요? ③ 있었으면 하는

"긴 제목을 넣으면 글자가 잘려요"        → 작은 문제 → task.md
"달력에서도 봤으면 좋겠어요"            → 큰 것    → intent.md 맨 위에 새 의도
"알림 기능"                             → 지금은 안 함 → 이유와

이어서 고치기:

/aml:go

▎ 버그 고치기는 실패하는 테스트/확인을 먼저 만들고 .aml/FIXING  이 동안 테스트 파일을 고치려 하면 안전망이 막습니다.
▎ 고친 뒤에는 spec.md 완성 기준에 한 줄이 영구히 남습니다 — - [x] 긴 제목도 잘리지 않는다 (2026-09-06 고침). 다음에 뭘 만들든 이 목록이 다시 확인됩니다.

그때그때 쓰는 3개

/aml:review          # 커밋 전에 한 번 더 보고 싶을 때
/aml:review 전체     # 한 달에 한 번, 예전 코드까지 통째로 점검
/aml:rule            # 같은 지적/실수가 두 번 나왔을 때 → 규칙으로 굳힘
/aml:status          # 어디까지 왔지? 지표 + 퀴즈
/aml:doctor          # 뭔가 이상할 때

/aml:rule 예:

/aml:rule
→ "progress.md 를 보니 '저장 확인을 빠뜨림'이 2번 나왔습니다.
→ 짧은 습관이라 CLAUDE.md 의 "Claude 가 자꾸 틀리는 것"에 한 줄 추가
   (순서가 있는 절차였다면 .claude/skills/<이름>/SKILL.md 규칙

한눈에

/aml:new  →  /aml:go  →  (직접 써 보기)  →  /aml:next  →  /aml:
   지도        만들기      ↑                  다음 바퀴      고치기
                        └ 중간에 언제든: /aml:status · /aml:ror

두 번째 기능부터는 /aml:new 로 다시 시작하면 되고, 그때 intent.E.md 규칙이 전부 이어집니다.
