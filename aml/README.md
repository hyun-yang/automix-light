# automix-light (aml) — 한국어판

> 첫 앱을 만드는 사람을 위한 Claude Code 플러그인입니다. automix를 가볍게 구성한 한국어 버전으로, 기획부터 구현, 검증, 사용 후 개선까지 안내합니다.

automix(am)는 기획 검증, 코드 리뷰, 팀 작업, 재사용 가능한 개발 패턴, 외부 모니터링 도구 연동을 지원합니다. automix-light는 이 중 혼자 첫 앱을 만들 때 필요한 기능을 중심으로 구성했습니다.

v0.6.0은 Anthropic의 [AI-Native SDLC 플레이북](https://claude.com/blog/the-ai-native-sdlc-playbook)을 바탕으로, **혼자 앱을 만드는 사람도 따라갈 수 있도록 개발 절차를 간소화한 버전입니다.** 핵심은 각 단계의 결과를 문서로 남기고, 다음 단계에서 그 문서를 기준으로 작업하는 것입니다. aml은 이 문서들을 초보자도 이해하기 쉬운 한국어로 작성합니다.

| 단계 | 기록하는 내용 |
|---|---|
| 기획 (`intent.md`) | 앱을 만드는 목적과 해결하려는 문제 |
| 요구사항 정의 (`spec.md`) | 필요한 기능, 완성 기준, 예상되는 문제 |
| 작업 계획 (`task.md`) | 작업 순서, 변경할 파일, 예상 위험, 검증 방법 |
| 구현 및 검증 (코드 + `progress.md`) | 구현 결과, 검증 결과, 소요 시간과 비용 |
| 코드 리뷰 | 버그, 보안 문제, 요구사항 충족 여부 |
| 사용 후 개선 | 작은 수정은 `task.md`에 추가하고, 새 기능이나 방향 변경은 `intent.md`에 정리 |

- **명령어 7개** — 기본 흐름은 `/aml:new` → `/aml:go` → `/aml:review` → `/aml:next`입니다. 필요에 따라 `/aml:rule`로 개발 규칙을 정리하고, `/aml:status`로 진행 상황을 확인하며, `/aml:doctor`로 작업 준비 상태를 점검합니다.
- **마크다운 중심 구성** — 명령어 정의, 템플릿, 작업 결과를 한국어 마크다운 문서로 관리합니다. 실행 코드는 작업 지표 기록 스크립트(`scripts/observe.py`, 파이썬 표준 라이브러리만 사용)와 작업 차단 훅(`hooks/aml-guard.sh`)으로 구성됩니다.
- **위험한 작업 차단** — 민감한 파일 커밋, 버그 수정 중 테스트 파일 변경, 강제 푸시 등 위험한 작업을 막고 이유와 해결 방법을 안내합니다.
- **별도의 검증 담당 에이전트** — 구현이 끝나면 `verifier` 에이전트가 직접 실행해 완성 기준을 충족하는지 확인합니다.

설계는 “A Field Guide to Fable”의 원칙을 참고했습니다. 프롬프트를 간결하게 작성하고, 제약 조건뿐 아니라 작업의 맥락을 전달하며, 시작 전에 불확실한 부분을 파악합니다. 처음 앱을 만들 때는 무엇을 결정해야 하는지부터 막막할 수 있습니다. 그래서 aml은 바로 구현하지 않고, 질문과 답변으로 요구사항을 정리하는 것부터 시작합니다.

## 설치

저장소를 내려받은 폴더에서 설치 스크립트를 실행합니다.

```bash
cd automix-light
./install.sh          # ~/.claude-marketplaces/automix-light에 복사합니다
```

그런 다음 Claude Code에서 다음 명령을 입력합니다.

```text
/plugin marketplace add ~/.claude-marketplaces/automix-light
/plugin install aml@automix-light
```

`/help`에 `/aml:new`, `/aml:go` 등 아래 명령어 7개가 표시되면 설치가 완료된 것입니다.

## 사용 흐름

### 1. `/aml:new "만들고 싶은 앱을 한 줄로 설명"`

먼저 프로젝트의 기본 설정을 준비합니다. `CLAUDE.md`(Claude Code가 매 세션 자동으로 읽는 프로젝트 안내)와 `REVIEW.md`(코드 리뷰 기준표)가 없으면 생성합니다. **이미 있는 파일은 수정하지 않습니다.** Git 저장소가 아니면 초기화하고 기본 브랜치를 `main`으로 설정합니다.

그다음 **`intent.md`**에 앱을 만드는 목적을 기록합니다. 질문과 답변으로 요구사항을 다듬기 전에 사용자의 원래 표현을 남겨, 이후에도 처음 의도를 확인할 수 있게 합니다.

요구사항을 구체화할 때는 다음 네 가지 관점으로 질문합니다.

| 구분 | 확인할 내용 | 진행 방식 |
|---|---|---|
| KK: 이미 알고 있는 내용 | 사용자가 명확하게 설명한 요구사항 | 설명한 내용을 그대로 기록합니다. |
| UU: 아직 생각해 보지 못한 내용 | 앱을 만들기 위해 추가로 결정해야 할 사항 | “보통 이런 항목을 정합니다”라는 예시 목록을 먼저 보여 줍니다. |
| KU: 결정이 필요한 내용 | 필요성은 알지만 아직 정하지 못한 사항 | 선택지가 있는 질문을 합니다. 추천을 요청할 수도 있습니다. |
| UK: 말로 설명하기 어려운 취향 | 원하는 화면의 분위기와 구성 | 서로 다른 목업 3~4개를 보여 주고 선택하도록 합니다. |

이 과정을 거쳐 `spec.md`와 `task.md`를 작성한 뒤 사용자에게 검토를 요청합니다. `spec.md`에는 완성 기준과 예상되는 문제를, `task.md`에는 작업 구간별 변경 파일, 위험, 검증 방법을 정리합니다. 문서의 항목명은 각각 **“걱정되는 것”**, **“바뀌는 파일 / 위험 / 증명”**입니다.

### 2. `/aml:go`

`task.md`의 작업을 순서대로 구현합니다. 각 작업은 다음 절차로 진행합니다.

1. **계획 확인** — 위험이 “낮음”이고 검증 방법이 정해져 있으면 자동으로 진행해도 되는 작업임을 안내합니다.
2. **구현** — 버그 수정은 **문제를 재현하는 실패 테스트 작성부터** 시작합니다. 화면 작업은 목업과 두세 차례 비교합니다. 계획이 달라지면 `task.md`도 함께 수정합니다.
3. **검증** — `CLAUDE.md`의 “확인하는 법”에 적힌 명령을 실행하고 결과를 보여 줍니다.
4. **기록** — `progress.md` 맨 위에 수행한 작업, 검증 결과, 메모, 작업 지표, 다음 작업을 기록합니다.
5. **커밋** — 작업 하나를 완료할 때마다 커밋합니다.

모든 작업이 끝나면 `verifier`의 별도 검증, 완성 기준 확인, 코드 리뷰, 최종 커밋 순서로 마무리합니다.

**작업 지표**는 작업마다 다음과 같이 한 줄로 기록합니다. 아래 수치는 형식을 보여 주기 위한 예시입니다.

```text
- 측정: claude-opus-4-8 · 4분 32초 · 토큰 입력 12.3k / 출력 4.1k (캐시 읽기 88k / 쓰기 2.1k) · 예상 비용 $0.42
```

사용한 모델, 소요 시간, 입력·출력 토큰 사용량, 예상 비용을 나타냅니다. 토큰은 모델이 텍스트를 처리하는 단위입니다. 비용은 공개 가격표를 기준으로 계산한 추정치이므로 실제 청구액과 다를 수 있습니다. `python3`가 없으면 `측정: 기록 없음`으로 표시하고 구현은 계속 진행합니다.

### 3. `/aml:review`

커밋 전에 `REVIEW.md`를 기준으로 **버그, 보안 문제, 요구사항 충족 여부**를 점검합니다. 리뷰 기준표에서는 각각 “버그”, “안전”, “약속 지킴”으로 표시됩니다. 요구사항 점검에는 `spec.md`의 완성 기준과 `task.md`의 계획을 따랐는지도 포함됩니다.

발견한 문제는 “중요”와 “사소”로 구분하며, 사소한 문제는 최대 5개까지 보고합니다. **리뷰에서는 코드를 수정하지 않습니다.** 필요한 수정은 `/aml:go`로 진행합니다.

`/aml:review 전체`를 실행하면 기존 코드를 포함한 전체 코드 점검도 할 수 있습니다.

### 4. `/aml:next`

완성된 앱을 직접 사용하면서 발견한 문제와 필요한 기능을 다음 작업에 반영합니다. 작은 수정은 `task.md`에 추가하고, 새 기능이나 방향 변경은 `intent.md`에 정리합니다.

수정한 버그는 `spec.md`의 완성 기준에 추가합니다. 이후 구현을 마칠 때 이 기준을 다시 확인해, 같은 문제가 재발했는지 점검합니다.

### 5. `/aml:rule`

같은 실수가 **두 번** 반복되면 예방 규칙을 문서로 남깁니다. 간단한 주의사항은 `CLAUDE.md`에 한 줄로 추가하고, 여러 단계가 필요한 절차는 규칙 카드(`.claude/skills/<이름>/SKILL.md`)로 작성합니다. 규칙 카드는 이후 세션에서 Claude가 관련 작업을 할 때 참고합니다.

### 6. `/aml:status`

진행 상황과 작업을 막고 있는 문제를 요약하고, 완성 기준 통과율, 반복된 리뷰 지적, 누적 시간과 비용을 보여 줍니다. 원하면 **퀴즈**로 자신이 만든 앱을 얼마나 이해하고 있는지도 확인할 수 있습니다.

### 7. `/aml:doctor`

작업 시작 전이나 문제가 생겼을 때 프로젝트 상태를 점검합니다. 파일은 수정하지 않습니다.

- ❌ **작업 전에 해결할 항목** — `spec.md`, `task.md`, `progress.md`가 없거나 완성 기준·작업 체크박스가 없으면 `/aml:new`를 안내합니다.
- ⚠️ **참고 항목** — `CLAUDE.md`, `intent.md`, `REVIEW.md`의 유무, 버그 수정 상태 파일(`.aml/FIXING`)의 잔류 여부, 작업 차단 기능, Git·`python3` 설치 여부, 설정 변경 후 검증 여부, Langfuse 설정을 확인합니다.

## 위험한 작업 차단

작업 차단 훅은 `spec.md`와 `task.md`가 있는 폴더에서 동작하며, 기본적으로 활성화되어 있습니다.

| 차단하는 작업 | 이유 |
|---|---|
| `.env` 파일 커밋 | 비밀번호와 API 키는 파일을 삭제해도 Git 기록에 남을 수 있습니다. |
| 버그 수정 중 테스트 파일 변경 | 테스트를 바꿔 오류를 통과시키면 실제 버그가 해결되지 않을 수 있습니다. |
| 강제 푸시, 하드 리셋, 대량 파일 삭제 | 작업 내용이나 기록이 사라져 복구하기 어려울 수 있습니다. |

비활성화하려면 `.aml/config.yaml`에 `guard: "off"`를 설정합니다. 자세한 동작과 프로젝트별 차단 규칙 추가 방법은 [작업 위임과 위험한 작업 차단](references/autonomy-and-guardrails.md)을 참고하세요.

## Langfuse 연동 (선택 사항)

[Langfuse](https://langfuse.com)는 LLM 작업 지표를 대시보드에서 확인하는 도구입니다. 연동하면 작업별 모델, 토큰 사용량, 소요 시간, 검증 결과가 전송되어 기능별 작업 흐름을 웹에서 볼 수 있습니다. **기본적으로 비활성화되어 있으며**, 연동하지 않아도 로컬 작업 지표 기록은 사용할 수 있습니다.

1. Langfuse 프로젝트(클라우드 또는 자체 호스팅)에서 public 키와 secret 키를 발급받습니다.
2. 키는 **환경변수로만** 설정합니다. 설정 파일에는 넣지 않습니다.
   ```bash
   export LANGFUSE_PUBLIC_KEY=pk-...
   export LANGFUSE_SECRET_KEY=sk-...
   export LANGFUSE_HOST=https://cloud.langfuse.com   # 자체 호스팅 시 해당 주소 사용
   ```
3. 프로젝트 루트에 `.aml/config.yaml`을 작성합니다.
   ```yaml
   langfuse: "on"        # "off"이거나 설정 파일이 없으면 전송하지 않음 (기본값)
   langfuse_host: ""     # 비우면 LANGFUSE_HOST 사용, 환경변수도 없으면 cloud.langfuse.com
   guard: "on"           # 작업 차단 기능: 기본 활성화, "off"로 비활성화
   ```
4. `/aml:doctor`로 연결을 확인합니다. “정상: Langfuse 연결을 확인했습니다”가 표시되면 설정이 완료된 것입니다.

네트워크 오류나 잘못된 키로 전송에 실패하면 경고를 남기고 구현은 계속 진행합니다.

## 사용 예시

```text
/aml:new "칸반처럼 쓰는 할 일 앱, HTML 파일 하나로"
  → Git 준비(기본 브랜치 main) + CLAUDE.md + REVIEW.md 생성
  → intent.md: "포스트잇으로 하던 걸 노트북에서 하고 싶다"
  → 결정할 항목 안내: 칸 개수, 마감일, 완료한 카드 처리, 드래그 이동 등
  → 선택지가 있는 질문 5개 → 목업 4개 → 3번 선택
  → spec.md + task.md + progress.md 생성, 검토 요청

/aml:go
  → 1.1 보드 화면 → 검증 → 작업 지표 기록 → 커밋
  → 1.2 카드 추가 창 → 같은 절차로 진행
  → verifier 검증 → 완성 기준 7개 모두 충족 → 리뷰 → 최종 커밋

/aml:review
  → 중요한 보안 문제 없음 / 사소한 문제 2개 → 결과 보고

/aml:next
  → "써 보니 카드가 많아지면 느려요" → task.md에 수정 작업 추가
  → "달력 보기도 있으면 좋겠어요" → intent.md에 새 기능 정리 → /aml:new
```

## automix(am)로 전환할 시점

여러 기능을 지속적으로 개발하면서 별도의 검증 단계(goal), 여러 에이전트의 협업, 프로젝트 간 개발 패턴 공유, 예산 상한, 되돌리기 명령이 필요해지면 automix(am)를 고려할 수 있습니다. 기획 → 작업 계획 → 구현·검증이라는 기본 흐름이 같아 aml에서 익힌 방식을 이어서 사용할 수 있습니다. am의 Langfuse 연동(`/am:observe`)도 같은 환경변수를 사용합니다.
