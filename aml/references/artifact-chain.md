# 기록 사슬 — 왜 파일로 남기나

aml 이 만드는 파일들은 "정리용 문서"가 아니다. **다음 단계가 실제로 읽는 입력**이다.

```
intent.md   왜 만들기로 했나          →  /aml:new 인터뷰의 출발점
spec.md     무엇을 만드나 · 완성 기준  →  /aml:go 의 검증 기준, /aml:review 의 "약속"
task.md     어떻게 만드나 · 위험 · 증명 →  /aml:go 가 따라가는 순서, 계획과 실제의 대조표
progress.md 무엇을 했나 · 측정 · 리뷰  →  /aml:status 의 지표, /aml:rule 이 캐는 반복 실수
REVIEW.md   무엇을 볼 것인가          →  /aml:review 가 매번 같은 눈으로 보게 하는 기준표
CLAUDE.md   이 프로젝트의 상식        →  모든 세션이 시작할 때 자동으로 읽는 파일
```

각 파일은 질문 하나에 답한다. 답이 겹치면 한쪽이 낡는다.

| 질문 | 답이 있는 곳 |
|---|---|
| 왜 이걸 만들지? | intent.md |
| 다 됐다는 걸 어떻게 아나? | spec.md 의 완성 기준 |
| 지금 뭘 하고 있지? | task.md 의 체크박스 |
| 왜 이렇게 만들었지? | progress.md 의 메모 |
| 이건 봐도 되나? | REVIEW.md |
| 어떻게 실행하지? | CLAUDE.md 의 확인하는 법 |

## 지킬 것 세 가지

1. **단계가 끝나면 커밋한다.** 커밋 하나하나가 "언제 무엇을 정했는지"의 증거다. 나중에 "왜 이렇게 했지?" 싶을 때 `git log` 가 답한다. 되돌리기도 커밋 단위로 한다.
2. **계획과 실제가 달라지면 계획을 고친다.** 코드만 바뀌고 task.md 가 그대로면, 다음에 읽는 사람(과 Claude)은 틀린 지도를 보게 된다. 같은 커밋에서 고치는 게 규칙이다.
3. **지우지 말고 쌓는다.** 지난 intent 는 intent.md 아래에, 고친 버그는 spec.md 의 완성 기준에, 한 일은 progress.md 에 남는다. 쌓인 목록이 다음번의 안전망이 된다.

## 다른 도구와 같이 쓸 때

노션·지라·트렐로에 이미 계획을 적고 있다면, 같은 내용이 두 곳에 생긴다. 그러면 **어느 쪽이 원본인지 하나만 정한다.**

- **저장소가 원본** (혼자 만들 때 가장 간단) — md 파일이 진짜 기록이고, 노션에는 링크만 붙인다.
- **도구가 원본** (팀이 이미 그 도구로 일할 때) — 노션·지라가 진짜 기록이고, 세션을 시작할 때 그 내용을 붙여 넣고 끝날 때 결과를 다시 옮긴다.
- **최소한 링크만이라도** — 양쪽에 서로의 주소를 적어 둔다. 원본이 둘이라는 걸 알고 쓰는 것과 모르고 쓰는 것은 다르다.

가장 나쁜 건 정하지 않는 것이다. 둘 다 조금씩 낡으면 어느 쪽도 믿을 수 없게 된다.

## 나중에 팀이 되면

이 사슬은 그대로 쓴다. 달라지는 건 읽는 사람이 늘어나는 것뿐이다 — PR 리뷰가 `spec.md`·`task.md`·`REVIEW.md` 를 읽고 "약속대로 만들어졌는지"를 본다. 자세한 건 `next-steps.md`.
