# 수정 구현 계획 검토

검토일: 2026-10-17. 대상: 현재 `spec.md`, `task.md`, 관련 템플릿·명령·설치 경로.

결론: `claude-code/`와 `codex/`로 나누는 구조와 Claude 이동부터 진행하는 순서는 적절하다. 다만 아래 네 항목은 구현 전에 계획에 반영해야 한다. 사용자 계획 파일은 수정하지 않았다.

## 1. 중요 — 공통 템플릿의 동일성 조건과 플랫폼별 수정 지시가 충돌한다

- 근거: [spec.md:12](spec.md#L12), [spec.md:26](spec.md#L26), [task.md:21](task.md#L21).
- 현재 `spec.template.md:31`에는 `.claude/skills/`, `progress.template.md:17`에는 `CLAUDE.md`가 있다. intent·review 템플릿에도 `/aml:*` 호출 예시가 있다.
- 계획대로 Codex 복사본에서 경로·이름만 변경하면 공통 템플릿 비교 테스트가 실패한다. 동일성을 지키려고 그대로 복사하면 Codex 사용자에게 Claude 경로를 안내한다.
- 권장 수정: 공통 5개에서는 “프로젝트 규칙 카드”, “프로젝트 안내 파일”, “기획/리뷰 스킬” 같은 중립 표현을 사용하고, 실제 플랫폼 경로·호출은 명령·스킬 본문과 전용 템플릿에서 안내한다. 그 뒤 두 복사본의 완전 일치를 검사한다.
- 작업 순서: 1단계의 기능 변경 없는 이동·검증을 마친 뒤, 2단계에서 양쪽 공통 템플릿의 안내 표현을 함께 정리한다. 파일 이동과 이 수정은 별도 변경으로 다룬다.
- 확인 기준: 공통 5개는 동일하고 플랫폼별 경로를 잘못 안내하지 않는다. 한쪽만 수정하면 비교 테스트가 실패한다.

## 2. 중요 — 양방향 이어가기에서 빠진 프로젝트 지침 파일을 준비하는 절차가 없다

- 근거: [spec.md:21](spec.md#L21), [task.md:30](task.md#L30), [task.md:81](task.md#L81).
- Codex `aml-new`는 AGENTS.md를 준비하도록 되어 있지만, Claude에서 만든 프로젝트를 Codex `aml-go`로 바로 이어갈 때 AGENTS.md가 없는 경우의 처리가 명시되지 않았다.
- 반대로 Codex에서 시작하면 CLAUDE.md가 없을 수 있다. 기존 Claude `go.md:27,41`은 CLAUDE.md의 검증 명령을 사용하므로, 문서 형식이 같다는 것만으로 반대 방향 실행이 보장되지 않는다.
- 권장 수정: 새로 기획하지 않고 플랫폼을 전환할 수 있는 준비 절차를 설치 안내 또는 doctor에 명시한다. 대상 도구의 지침 파일이 없으면 기존 프로젝트의 실행·검증 정보를 바탕으로 생성하고 기존 파일은 보존한다. 충돌하는 지침은 임의로 덮어쓰지 않는다.
- Claude의 “기능 변경 없이 이동” 원칙을 유지하려면 최초 전환 시 사용자가 수행할 명시적인 준비 절차로 제공할 수 있다. Claude go에 자동 처리를 추가하려면 이동 이후 별도 기능 변경으로 계획한다.
- 확인 기준: 각 방향에 대해 대상 도구의 지침 파일이 처음에는 없는 임시 프로젝트로 시험한다. 준비 후 기존 task 체크 상태·진행 기록을 유지하면서 작업과 검증을 이어간다. 두 방향을 각각 독립적인 완료 항목으로 둔다.

## 3. 중요 — Codex 샌드박스·승인 설정이 기존 AML 훅을 대신한다고 읽힐 수 있다

- 근거: [spec.md:25](spec.md#L25).
- “되돌리기 어려운 일을 막는 훅은 없고, Codex의 샌드박스·승인 설정이 담당한다”는 기준은 보호 범위를 과장할 수 있다. 샌드박스·승인의 실제 설정에 따라 허용 범위가 다르며, 그것만으로 AML의 비밀키 접근·FIXING 중 테스트 변경 차단 규칙이 동일하게 적용된다는 근거는 없다.
- 권장 문구: “이 버전에는 AML 전용 차단 훅이 없습니다. Codex의 권한·샌드박스·승인 설정은 환경에 따라 적용되며, Claude판 AML 훅과 같은 차단을 보장하지 않습니다.”
- 확인 기준: doctor와 README가 AML 전용 차단 미제공을 명확히 알린다. 환경의 실제 설정을 확인하지 않았다면 보호가 켜져 있다고 단정하지 않는다. 훅이 없다는 이유만으로 기획·구현 진행을 막지는 않는다.

## 4. 중요 — 측정 구현·테스트보다 실제 워크플로우 검증이 먼저다

- 근거: [task.md:28](task.md#L28), [task.md:44](task.md#L44), [task.md:54](task.md#L54).
- 3단계에서 new→go→status의 실제 흐름을 검증하지만, 측정과 summary 구현은 5단계, 해당 테스트는 6단계다. 현재 순서로는 측정 실패를 정상 처리하는 것만 확인한 뒤 핵심 흐름을 검증했다고 볼 수 있다.
- 5단계의 “구간 사용량 합산”도 세션 선택·누적값 처리 기준이 없다. 같은 폴더에서 여러 세션을 실행하거나 누적 토큰을 매 이벤트마다 더하면 다른 작업의 사용량을 섞거나 중복 계산할 수 있다.
- 권장 수정: 스킬 초안을 먼저 만드는 것은 가능하지만, 실제 go→status 검증은 측정·summary 구현 이후로 옮긴다. 측정 테스트는 구현 단계에 함께 배치한다.
- 최소 측정 기준: 현재 작업에 해당하는 세션 식별, 구간 시작/종료 누적값의 차분, 프로젝트와 세션 격리, 캐시 토큰 중복 계산 방지, 미지원 형식의 명시적 미수집 처리. 측정 행이 출력되는지만 검사하지 말고 가짜 기록의 기대 숫자와 비교한다.
- 비용은 지원할 모델·단가 출처·미지원 모델 처리 기준을 정한다. 모르는 모델의 비용을 0으로 표시하지 않는다. 실세션 숫자 출력 확인은 계산 정확성 테스트를 보완하는 확인으로 둔다.
- summary는 Claude/Codex 측정 줄이 섞인 progress.md, 측정 없는 작업, 다중 모델을 포함하는 예시로 검증한다.

## 그 밖의 보완 사항

- **미확정 범위 표시:** [spec.md:39](spec.md#L39)에 Codex의 로컬 측정·Langfuse 미제공이 “확인 필요”로 남아 있다. Claude의 기존 Langfuse 보존과는 별개로, Codex 첫 버전에서 전송을 제공하지 않는 범위를 최종 확인하고 확정 표시해야 한다.
- **지원 환경 명시:** [task.md:18](task.md#L18)의 `codex-cli 0.163.0`은 시험 대상 버전이다. 첫 지원 범위를 로컬 CLI로 제한하는지, IDE/desktop도 포함하는지 spec에 명시하고 시험하지 않은 환경은 보장하지 않는다.
- **설치 시험 격리:** 기존 AML을 끄기 위해 실제 사용자 설정부터 바꿀 필요는 없다. 가능하면 별도 시험용 설정·캐시 환경에서 설치를 검증하고, 실제 설치 전환은 사용자가 정한 승인 조건을 따른다. 이번 검토에서는 설정을 변경하지 않았다.
- **완료 조건의 검색 범위:** [task.md:68](task.md#L68)의 옛 경로 “0건”은 실행 안내·유효 링크를 대상으로 한정한다. 이동한 분석 문서의 과거 경로 설명이나 `cd claude-code` 뒤의 `./install.sh`는 정당한 기록·명령일 수 있다.
- **문서 간 결정 일치:** intent.md의 미정 목록에는 이미 spec에서 정한 브랜치 활용·템플릿 비교 방식 등이 남아 있다. 확정 사항과 미정 사항을 구분하면 구현 중 다시 판단하는 일을 줄일 수 있다.

## 확인한 범위

현재 설치 스크립트와 두 smoke test는 자기 파일 위치 기준으로 경로를 계산하므로 네 묶음을 같이 옮기는 계획과 맞는다. `codex-migration` 브랜치 존재 및 로컬 `codex-cli 0.163.0`을 확인했다. CLI help에서 로컬 marketplace 경로 등록 명령은 확인했으나 `codex/` 중첩 구조를 실제로 등록·설치하지는 않았다.

이번 검토에서는 파일 이동, 제품 구현, 테스트 실행, 사용자 설정 변경을 하지 않았다. 이 검토 문서만 추가했다.
